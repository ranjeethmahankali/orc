*** Custom Rendering (not egui-snarl or egui-graph-edit)

    Existing egui node editor crates (egui-snarl, egui-graph-edit) maintain their own internal graph
    model with their own ID types. Using them would require keeping two parallel graph representations
    in sync -- a constant source of bugs. Instead, render nodes directly from the orc Workflow using
    egui's Painter API:

    - ~Painter::rect_filled~ / ~rect_stroke~ for node bodies (rounded rectangles)
    - ~Painter::circle_filled~ / ~circle_stroke~ for input/output pins
    - ~Painter::text~ for all labels (monospace font throughout the entire UI)
    - ~Painter::add(Shape::CubicBezier { .. })~ for connection curves between pins

    All coordinates are transformed through a pan/zoom affine matrix before drawing.

*** Force-Directed Layout with DAG Flow Constraint

    Nodes are NOT draggable. The layout is computed automatically by a force-directed simulation
    that respects left-to-right DAG flow. Nodes are axis-aligned rectangles with variable sizes
    (inspect nodes are resizable). The layout updates incrementally when topology changes or nodes
    are resized. Positions and sizes are not persisted to disk for now -- they are recomputed from
    scratch when the app opens, and updated in-place during the session.

**** Forces

     - *Bounding-box repulsion:* All node pairs repel each other based on their bounding boxes
       (not point-to-point). Larger inspect nodes push neighbors further away. This prevents
       overlap and maintains readable spacing.
     - *Spring attraction along edges:* Connected nodes (output pin -> input pin) are pulled
       toward each other. Spring rest length is proportional to the sum of the two nodes' widths
       plus a gap.
     - *Vertical centering:* Each node is gently pulled toward the vertical median of its
       connected neighbors, reducing unnecessary vertical spread.

**** DAG Flow Constraint (hard constraint)

     After each simulation step, enforce left-to-right ordering: for every edge (A -> B), ensure
     ~B.x >= A.x + A.width + gap~. If violated, push B rightward. This is applied in topological
     order so that corrections propagate downstream in a single pass.

     Workflow input chips are pinned to x = 0. Workflow output chips are free to settle at whatever
     x the simulation produces (they will naturally end up rightmost since they have no downstream
     nodes pulling them left).

**** Initial Seeding (app startup, no stored positions)

     1. Topological sort gives each node a depth (longest path from any root).
     2. Depth determines initial x position (depth * (typical_node_width + gap)).
     3. Nodes at the same depth are spread evenly along y.
     4. Run full simulation to convergence (iterate until max force magnitude drops below a
        threshold, or a fixed max iteration count is reached).

**** Incremental Updates (topology change, node resize)

     When a node is added, removed, connected, disconnected, or resized:
     1. Keep all existing node positions as-is.
     2. New nodes are seeded near their connected neighbors (or at the center of the viewport if
        disconnected).
     3. Re-run the simulation from current positions for a few iterations until convergence.
     4. Because the simulation is continuous (small perturbation -> small output change), the layout
        shifts smoothly without large jumps.

**** Convergence and Repaint

     The simulation runs as part of the update loop. While forces are above the convergence
     threshold, ~ctx.request_repaint()~ is called each frame to animate the layout settling. Once
     converged, repaints stop (zero CPU). This gives a smooth animation of nodes settling into
     place after a topology change.

*** Hit Testing via Spatial Hash Grid

    Nodes have variable sizes (resizable inspect nodes) and are not in strict layers, so a general
    spatial index is needed. A spatial hash grid provides O(1) average-case point queries.

**** Structure

     A uniform grid where each cell is roughly the size of a typical node (~200x200 canvas units).
     Each node is inserted into all grid cells its bounding box overlaps. A large resized inspect
     node may span several cells -- this is fine.

**** Queries

     To find what is under the cursor:
     1. Transform cursor to canvas coordinates.
     2. Compute grid cell from canvas position.
     3. Test only nodes in that cell (and possibly immediate neighbors for edge cases).
     4. If the cursor is on a node, test its pins linearly (few pins per node).

**** Rebuild

     The grid is rebuilt whenever the layout changes (topology change, resize, or simulation step).
     Rebuild cost is O(n) -- iterate all nodes, insert into cells. This is cheap even for thousands
     of nodes.

*** EditorState

    Uses orc's existing property system (~NodeProperty<T>~, ~OutputProperty<T>~) instead of
    HashMaps. Properties are attached to the workflow's graph and automatically resize when nodes
    are added/removed or garbage collection runs.

    Positions and sizes are transient -- not persisted to disk. They are computed by the layout
    simulation on app startup and updated in-place during the session. Persistence of UI state is

*** Incremental Execution

    <2026-09-09 Wed> Brainstormed the execution engine and threading model in detail. Nesting is
    out of scope for now -- see Phase 5, which is where ~NestedExecState~ (below) actually
    belongs; this section only covers a flat, non-nested workflow. Dagger gets its own executor,
    separate from ~Workflow::run~ -- that function is a live public API other hosts depend on
    (pyorc's ~run_workflow~, ~kbb_cli_host~'s tests both call it with its current
    signature/behavior), so it stays as-is rather than growing incremental/threading concerns
    bolted on.

**** Why every node is a root

     ~Workflow::run~'s traversal starts only from ~self.workflow_outputs~ (the explicit named
     terminal outputs set via ~set_outputs~). Dagger never calls ~set_outputs~/~set_inputs~, so
     that list is always empty here, and Inspect nodes -- dead ends, no outputs -- would never be
     reached by that traversal at all. Dagger's own executor instead walks every node
     (~workflow.node_iter()~ as roots, same shape as ~layout::compute_depths~), so Inspect dead
     ends and anything else get evaluated regardless of whether they feed a declared output.
     Nodes flagged as part of a cycle are skipped -- but the executor does its own cycle check
     each time it walks, rather than trusting ~state.node_in_cycle~, which ~layout::compute_layout~
     only ever computes once (the first ~measure~ call) and does not update after later
     topology edits.

**** Staleness tracking

     - ~computed_outputs: OutputProperty<Arc<OrcHandle>>~ in ~EditorState~, cached per output
       pin (~Arc~-wrapped -- see "Handle lifetime across threads" below). The "not yet computed"
       sentinel is ~free_fn.is_none()~ on the wrapped handle (the zeroed default) -- *not*
       equality against a zeroed ~handle~ id, since ~HANDLE_COUNTER~ starts at 0 and a
       legitimately computed value could be assigned handle id 0. Only ~free_fn~ tells "no
       backing deck" apart from "really is handle 0", matching the pattern already used
       elsewhere in the crate (e.g. the constant-deletion regression test in ~interaction.rs~).
     - ~dirty_version: NodeProperty<u64>~ per node, bumped (not just set to a bool) on a direct
       edit -- connect, disconnect, add, delete, a constant's value changing -- and propagated
       forward to every downstream node. This requires a small addition to ~orc_sdk~: a public
       forward-adjacency accessor on ~Workflow~ (e.g. ~output_links(OH)~), thinly wrapping the
       ~Graph::output_links~ machinery that already exists internally (an intrusive linked list
       per output, walked in O(fan-out)) but isn't reachable from outside the crate today --
       ~Workflow~ only exposes the backward lookup (~input_source~).
     - Dispatch readiness is tracked via a small worklist of "candidate" nodes -- anything just
       touched by a staleness-propagation pass, or whose upstream just finished computing -- each
       checked locally against its own (small) fan-in when popped. This is deliberately not a
       fully precise per-edge in-degree counter (more bookkeeping than it is worth at typical
       node arity) and not a per-frame full-graph scan either -- work stays proportional to
       whatever actually changed, not to graph size.

**** Thread pool

     A fixed-size pool of ~max(available_parallelism() - 1, 1)~ long-lived worker threads,
     spawned once and blocking on a shared ~Arc<Mutex<Receiver<NodeJob>>>~ -- no thread creation
     or teardown during interactive use, and independent branches genuinely run in parallel
     (whichever worker is free picks up the next ready job), which is the whole reason for a pool
     over a single background thread. A single-background-thread design was considered and
     rejected: it's simpler and sidesteps the handle-lifetime issue below, but gives up true
     cross-branch parallelism, which is a hard requirement here, not a nice-to-have.

     Results come back over a second ~mpsc~ channel, drained via ~try_recv()~ on the UI thread
     once per frame -- the UI thread never blocks on execution, matching or exceeding the
     original 100ms-poll idea.

     ~NodeJob~ carries everything a worker needs without ever touching the live ~Workflow~ (whose
     ~Rc~/~RefCell~-based properties are not ~Send~): the node handle, the plugin function
     pointer, its inputs as cloned ~Arc<OrcHandle>~ (see "Handle lifetime across threads" below),
     the output count, a cancellation ~ctx~ id, and the ~dirty_version~ it was launched for.
     ~NodeResult~ carries the node handle, that same ~ctx~/launched version, and the outcome:
     ~Ok(outputs)~, ~Err(OperationCancelled)~, or ~Err(other)~.

**** Cancellation is per node job, not per pass or global

     One ~ContextArena<bool>~ slot per dispatched job (mirrors the existing
     ~SERIAL_CONTEXT_ARENA~ pattern already used for ~serial_write_callback~). The plugin's
     ~check_cancellation(ctx)~ callback reads it; whether a plugin checks it at all is entirely
     up to whoever implemented that node -- the host impose no policy here. Only the specific job
     whose own node gets invalidated has its flag flipped: editing an unrelated, independent
     branch must never disturb a node that is currently running, since its output is still
     perfectly valid. This relies on ~ORC_ERROR_OPERATION_CANCELLED~ (added in commit e1b1320) to
     tell a cooperative abort apart from a real failure returned by the same call.

**** Handle lifetime across threads: ~Arc<OrcHandle>~

     ~OrcHandle~ already has ~impl Drop { fn drop(&mut self) { self.free(); } }~ (~ffi.rs:212~) --
     dropping an owning handle calls ~.free()~, dropping a borrowed one (~free_fn: None~, as
     produced by ~.borrowed()~) is already a safe no-op. It's a move-only, RAII-owning type
     already (why ~Workflow::run~ has to ~std::mem::take~ out of ~computed_outputs[o.idx]~
     instead of just reading it). So sharing one across an in-flight job needs nothing more than
     the standard tool for shared ownership: ~computed_outputs: OutputProperty<Arc<OrcHandle>>~.

     Dispatching a job clones the ~Arc~ for each borrowed input and stores the clones directly in
     ~NodeJob~. On the worker, right before the actual plugin call, an ~OrcHandleBorrowed<'_>~ is
     derived locally from each ~Arc<OrcHandle>~ (~arc.borrowed()~) into a short-lived stack
     buffer -- an ordinary, fully compiler-checked borrow, since the owning ~Arc~ clones are
     sitting on the same stack frame the whole time. ~OrcHandleBorrowed~ never has to cross the
     channel or have its lifetime unsafely asserted away; only the ~Arc~ travels, and it's
     ordinarily ~Send~.

     Committing a fresh result is just ~computed_outputs[oh] = Arc::new(new_handle)~. If the UI
     thread held the only reference, the old ~Arc~ drops immediately and ~.free()~ runs right
     there, via ~OrcHandle~'s own ~Drop~ -- nothing in dagger calls ~.free()~ explicitly anywhere.
     If some worker still holds a clone (an in-flight downstream job that captured the old
     value), the old ~Arc~ simply lives on until that worker drops its copy, whereupon ~.free()~
     runs automatically -- on whichever thread happens to drop last, which is why a plugin's
     ~free_fn~ must be safe to call from any thread (the same expectation the whole design
     already places on plugin code called concurrently in general). No reader-count bookkeeping,
     no pending-commit staging slot, no ~orc_sdk~ changes at all -- this works uniformly for
     built-in and plugin-owned handles alike, since it never needs to look behind the handle at
     what's managing the actual backing memory (which, for a plugin-owned type, may not even be
     Rust).

     Relies on one existing invariant: the executor always allocates a *fresh* handle id per
     computed output (never reuses one), matching how ~Workflow::run~ already works via
     ~handle_counter.fetch_add~. ~DeckRegistry::alloc_with_value~ has a same-id-reuse path
     (~util.rs:134~) that mutates a built-in deck's contents in place under a write lock when the
     id is already occupied with a matching type -- irrelevant as long as the executor never
     reuses an id, but worth remembering if that ever changes.

**** Commit policy on job completion

     - ~Ok(outputs)~ is always committed immediately (replacing the ~Arc<OrcHandle>~ in
       ~computed_outputs~ -- no staging needed), even if the node was invalidated again after
       this job launched -- a stale-but-real value beats showing
       nothing, and this is exactly what makes continuously dragging a slider feel alive while a
       slow, non-cooperative node is mid-flight. The node is still redispatched afterward if it's
       still marked dirty.
     - ~Err(OperationCancelled)~ commits nothing; the node is simply eligible for redispatch again
       right away.
     - Any other ~Err~ is a genuine fault: shown on the node, and the node settles rather than
       retrying every time the scheduler looks for ready work -- it only becomes a candidate
       again once a future edit actually touches it or its inputs.

**** In-progress indicator

     A node with an in-flight job gets a looping left-to-right pulse/sweep drawn into its title
     bar fill (indefinite-progress-bar style), driven by wall-clock time. Continuous repaint is
     requested every frame while any node is in-flight -- gated on "something is actually
     running", so it costs nothing the rest of the time, but needed for the sweep to animate
     smoothly (a 100ms poll interval, as originally planned, would make it stutter).

*** Repaint Strategy

    Reactive mode -- zero CPU when fully idle. ~ctx.request_repaint()~ is called only when needed:

    - Canvas interaction: pan, zoom, box select
    - Pin connection wire drag (drawing the in-progress Bezier to the cursor)
    - Inspect node interaction: scrolling text content, resizing the inspect viewport, future
      pan/zoom/orbit within an embedded 2D/3D viewport
    - Layout settling: stale -- Phase 3b removed the force-directed simulation entirely, so this
      no longer applies. Layout is now a one-shot computation (see "Force-Directed Layout with
      DAG Flow Constraint" above, itself written before that removal).
    - Execution: continuous repaint every frame while any node has an in-flight job (both to
      drain the results channel and to animate the in-progress sweep on that node's title bar --
      see "In-progress indicator" under "Incremental Execution"). Replaces the original
      100ms-poll idea, which would make the sweep stutter. Stops the instant nothing is running.

    When no interaction is active, no layout is settling, and no execution is running, the app
    sleeps completely and consumes zero CPU.

  dependency feature into a crate feature of its own, defaulted on. With =extension-module=
  enabled, pyo3 skips linking libpython at build time, since a real Python extension module gets
  those symbols for free from the host interpreter that =dlopen='s it at import time. A =cargo

  undefined references if =extension-module= is on.

  =pyo3/extension-module=, and default it on. =maturin build= / =maturin develop= build with
  default features, so the wheel is unaffected. Tests are run with =cargo test
  --no-default-features=, which turns the forwarding feature off so pyo3's build script links
  against libpython normally. Also switched =crate-type= to =["cdylib", "rlib"]=, since a pure
