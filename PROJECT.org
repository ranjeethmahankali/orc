* TODO Thread Safety in C SDK
  :PROPERTIES:
  :CREATED:  2026-06-07 Sun 15:12
  :END:

  Whenever the plugin code receives an output handle from the host, it has to
  verify that the output handle was allocated in the same plugin. Otherwise it
  is unsafe to write into that memory address. If it came from another plugin,
  then this plugin cannot know anything about the datatype or memory layout. To
  check for this, each plugin likely needs to keep a global list of allocated
  decks, and ensure the output handle matches one of them. Access to this global
  list should be thread safe, since the host can call the plugin functions from
  any thread.

  While this is trivial to do in C++ and Rust, it is not trivial to do in a
  cross platform manner in C. For now, I just have a dummy check that always
  returns true (safe). This is good enough for a prototype, but at some point we
  need to figure out a good cross platform thread API for our C SDK.

  Should the host provide the thread API too? How does Parasolid handle it?

* NEXT tj92sq - OrcHandle Lifetimes and Identity
  :PROPERTIES:
  :CREATED:  2026-08-04 Tue 09:32
  :END:
  :LOGBOOK:
  - State "NEXT"       from "TODO"       [2026-08-04 Tue 10:56]
  :END:

  Handles pointing to data from one plugin can be passed in as inputs to any other plugin. This
  works fine, because input handles are immutable. It is unclear what should happen when the host
  passes in one of those handles as an output handle. In the current state, we will get some type of
  UB / crash. This is a serious liability for the design and needs to be fixed ASAP.

  Whatever solution I come up with, must make it hard to do the wrong thing, without creating too
  much friction. Ideally the host keeps the output handles of each block separate and doesn't mix
  and match them, but that becomes less clear when dealing with container operation blocks, that
  request the host to allocate decks in other plugins, of types that it doesn't recognize.

  - Should the host think of the resulting deck as belonging to the plugin that implemented the
    container op, or the plugin that created the deck from a proxy deck?
  - What happens when the output datatype of a container operation is a primitive type that is
    recognized by all plugins and the host? Who is responsible for the output then?
  - The meaning of the ~handle~ property of ~OrcHandle~ can be different in each plugin. What if I
    take an OrcHandle from plugin A, and pass it to plugin B, which also just happens to contain
    something in it's registry with the same ~handle~?

  This all feels like a mess, and needs to be solved immediately, otherwise the whole C API effort
  can fall apart.

  Should the host take ownership of the ~handle~ property and assign it, and make sure it is
  globally unique? And the plugins just use the host assigned ~handle~ as a unique identifier?

** Design

   - ~OrcHandle~ owns its backing data via ~free_fn~. ~OrcHandle const*~ is a read borrow.
     ~OrcHandle*~ is a write borrow. The host owns the handle slots and lends access to plugins.
   - The host assigns ~handle.handle~ (a ~uint64_t~ ID) to every slot before lending it to any
     plugin. No one ever modifies ~handle.handle~ again, even when the backing data is freed.
   - Each plugin maintains a global registry (~uint64_t → deck_ptr~) for the handles it owns.
     Ownership check: look up the ID in the registry. If found → this plugin owns it. If not →
     someone else does (or the slot is empty, indicated by ~free_fn == NULL~).
   - When a plugin receives write access (~OrcHandle*~) to a handle it does not own, it calls
     ~handle->free_fn~ to evict the current owner, then allocates new backing data for that ID.  The
     host guarantees no concurrent read access exists when write access is lent out.
   - ~handle.handle~ survives ~free_fn~. All other fields are zeroed on free.
