* TODO Objectify Test
  :PROPERTIES:
  :CREATED:  2026-06-07 Sun 15:19
  :END:

  =Objectify= is a Grasshopper plugin that I wrote a long time ago. It is a very
  good litmus test to judge the quality of this new system, once enough details
  are fleshed out. =Objectify= implements structs on top of Grasshopper. The
  user can compose arbitrary data into their own struct, pass it around their
  file, and later access members of that struct. It is a minor convenience, and
  was trivial to implement in GH. Trying to do the same in Kratos turned into a
  dumpster fire. That is what makes this a good litmus test.

  <2026-08-01 Sat 18:42> It seems fairly trivial to do this with built-in types, and with types that
  are internal to the plugin that is trying to implement this. Just make a generic dictionary type
  that stores all data in a tagged union, or a heap allocated OOP thing or whatever. And make a
  block that takes variadic inputs of different types, and names, and outputs a this dictionary. The
  first input could be a list of names, and the remaining inputs could each represent one member of
  the object / dictionary. Probably fine to do the usual list processing on such inputs, but
  requires a bit of thought.

  It seems very unwieldy to try and get this to work with types that are opaque to another
  plugin. That would require some sort of shared strategy between the plugins, and possible between
  the host and the plugins, for type erased storage of objects in a container. That can be done in
  theory with something that resembles a v-table, but not worth it. Very ugly, and likely not useful
  at all. This is possible trivially in C# (Grasshopper), because it is C#.

  :PROPERTIES:

  :END:

  This would be super useful for sharing data types such ~glm::dvec3~, and other ~glm~ primitives
  and similar datatypes in other languages and libraries, across the FFI boundary, without the fuss
  of creating new datatypes. This is not absolutely essential, but makes interoperability across
  plugins much easier. Rigght now the primitive type_id, and item_size are two separate fields of
  ~OrcHandle~. This is enough to let the receiver know that the data is an aggregate array of said
  primitive. E.g. a handle with type f64, and item size of 24 bytes automatically implies an array
  of 3 doubles. Each item of the deck is a fixed size arrary of 3 doubles. The combinations, the
  striding logic etc. in the C SDK already respect the item_size, and stride over the 24 bytes. So
  the C SDK can already work this way with minimal changes, as long as the owner / sender of the
  handle properly assigns these fields. On the Rust side, [[file:rust/orc_sdk/src/deck.rs::pub fn get_input<T: Default>(&self, items: &'a \[T\], index: usize) -> DeckView<'a, T> {][this function]] just needs to be invoked
  with type ~[f64; 3]~ (e.g. when item size is 24 bytes) and the items is of type ~&[[f64;
  3]]~. Presumabley something upstream in the Rust's orc_fn (macro expansion) checks the item size
  before casting the items pointer to a slice of that type.

  Need to think a bit more about how the handles are created on the side of the plugins that own
  these datatypes. E.g. a Rust plugin that owns a ~Deck<glam::DVec3>~, and a C++ plugin that owns a
  ~Deck<glm::dvec3>~ or an equivalent C deck, should all produce an identical handle.

   Progress so far: ~orc_sdk_handle_alloc~/~orc_deck_alloc~ (C SDK + ABI) now take an
   explicit ~item_size~, validated as a multiple of the primitive's intrinsic size, and
   this fixed a real latent bug in ~orc_sdk_deck_from_proxy~ (it used to size the initial
   allocation from the scalar's intrinsic size, then separately grow to the real item_size,
   desyncing the allocator bookkeeping for anything that wasn't a primitive). Clean rebuild,
   0 warnings, all 277 C/C++ tests pass. Decided the ABI-exported ~orc_deck_alloc~ itself was
   dead weight -- nothing in any host (~dagger~, ~server_host~, ~kbb_cli_host~, ~pyorc~) ever
   called the loaded symbol in production, since outputs are allocated automatically when a
   plugin function runs (~registry_.alloc::<T>()~ on the Rust side, direct
   ~orc_sdk_handle_alloc~ calls in C plugin bodies) -- so it was deleted outright from
   ~orc_abi.h~, ~orc_sdk.h~/~.c~, and the Rust side (~ffi.rs~'s ~orc_plugin!~ macro,
   ~DeckAllocFn~, ~host.rs~'s ~Plugin::load~/~alloc_deck~). Workspace builds clean,
   ~cargo run -p bindings_generator -- c/orc_abi.h --rust-check rust/orc_sdk/src/bindings.rs~
   is back in sync. One loose end from that deletion: ~TOrcPluginAdaptor::deck_alloc~
   (~rust/orc_sdk/src/ffi.rs:302~) and its one implementation
   (~rust/example_rust_plugin/src/lib.rs~) are now unreachable and should be removed too.

   Remaining work, to take one at a time:

   1. [X] *C:* ~orc_sdk_deck_from_proxy~'s multi-input loop (~orc_sdk.c~, right before the
      ~orc_sdk_handle_alloc(id, item_size, out)~ call) only checks that all inputs share the
      same ~type_id~, not the same ~item_size~. That equality used to be implied for free --
      same type_id meant same primitive meant same size. Once one type_id can carry several
      item sizes, ~ORC_DECK_PROXY_SHUFFLE~ (the one proxy mode that legitimately takes more
      than one input deck) will silently accept a scalar F64 deck and an F64x3 deck in the
      same shuffle and copy items using ~item_size~ taken from input 0 regardless of which
      input a given proxy item actually points to -- wrong-width copies, no error. Needs an
      ~inputs[i].item_size != item_size~ check alongside the existing type_id check.
   2. [X] *C:* the ~item_size % single_item_size~ validation in ~orc_sdk_handle_alloc~ doesn't
      reject ~item_size == 0~ (~0 % anything == 0~, so it passes). That allocates a deck
      whose header records ~item_size = 0~; every item-index computation
      (~index * item_size~) collapses to the same address, so every "item" silently aliases
      the same memory instead of erroring out. Needs an explicit ~item_size == 0~ rejection.
      Neither of these two is exercised by any existing test -- the new validation branch has
      no coverage in either direction (success or rejection).
   3. [X] *Rust, the actual enabling piece:* there is still no ~TOrcData~ impl for any aggregate
      type -- only the primitives (~u8~..~i64~, ~f32~, ~f64~, ~OrcItemProxy~) implement it.
