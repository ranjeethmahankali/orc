*** Custom Rendering (not egui-snarl or egui-graph-edit)

    Existing egui node editor crates (egui-snarl, egui-graph-edit) maintain their own internal graph
    model with their own ID types. Using them would require keeping two parallel graph representations
    in sync -- a constant source of bugs. Instead, render nodes directly from the orc Workflow using
    egui's Painter API:

    - ~Painter::rect_filled~ / ~rect_stroke~ for node bodies (rounded rectangles)
    - ~Painter::circle_filled~ / ~circle_stroke~ for input/output pins
    - ~Painter::text~ for all labels (monospace font throughout the entire UI)
    - ~Painter::add(Shape::CubicBezier { .. })~ for connection curves between pins

    All coordinates are transformed through a pan/zoom affine matrix before drawing.

*** Force-Directed Layout with DAG Flow Constraint

    Nodes are NOT draggable. The layout is computed automatically by a force-directed simulation
    that respects left-to-right DAG flow. Nodes are axis-aligned rectangles with variable sizes
    (inspect nodes are resizable). The layout updates incrementally when topology changes or nodes
    are resized. Positions and sizes are not persisted to disk for now -- they are recomputed from
    scratch when the app opens, and updated in-place during the session.

**** Forces

     - *Bounding-box repulsion:* All node pairs repel each other based on their bounding boxes
       (not point-to-point). Larger inspect nodes push neighbors further away. This prevents
       overlap and maintains readable spacing.
     - *Spring attraction along edges:* Connected nodes (output pin -> input pin) are pulled
       toward each other. Spring rest length is proportional to the sum of the two nodes' widths
       plus a gap.
     - *Vertical centering:* Each node is gently pulled toward the vertical median of its
       connected neighbors, reducing unnecessary vertical spread.

**** DAG Flow Constraint (hard constraint)

     After each simulation step, enforce left-to-right ordering: for every edge (A -> B), ensure
     ~B.x >= A.x + A.width + gap~. If violated, push B rightward. This is applied in topological
     order so that corrections propagate downstream in a single pass.

     Workflow input chips are pinned to x = 0. Workflow output chips are free to settle at whatever
     x the simulation produces (they will naturally end up rightmost since they have no downstream
     nodes pulling them left).

**** Initial Seeding (app startup, no stored positions)

     1. Topological sort gives each node a depth (longest path from any root).
     2. Depth determines initial x position (depth * (typical_node_width + gap)).
     3. Nodes at the same depth are spread evenly along y.
     4. Run full simulation to convergence (iterate until max force magnitude drops below a
        threshold, or a fixed max iteration count is reached).

**** Incremental Updates (topology change, node resize)

     When a node is added, removed, connected, disconnected, or resized:
     1. Keep all existing node positions as-is.
     2. New nodes are seeded near their connected neighbors (or at the center of the viewport if
        disconnected).
     3. Re-run the simulation from current positions for a few iterations until convergence.
     4. Because the simulation is continuous (small perturbation -> small output change), the layout
        shifts smoothly without large jumps.

**** Convergence and Repaint

     The simulation runs as part of the update loop. While forces are above the convergence
     threshold, ~ctx.request_repaint()~ is called each frame to animate the layout settling. Once
     converged, repaints stop (zero CPU). This gives a smooth animation of nodes settling into
     place after a topology change.

*** Hit Testing via Spatial Hash Grid

    Nodes have variable sizes (resizable inspect nodes) and are not in strict layers, so a general
    spatial index is needed. A spatial hash grid provides O(1) average-case point queries.

**** Structure

     A uniform grid where each cell is roughly the size of a typical node (~200x200 canvas units).
     Each node is inserted into all grid cells its bounding box overlaps. A large resized inspect
     node may span several cells -- this is fine.

**** Queries

     To find what is under the cursor:
     1. Transform cursor to canvas coordinates.
     2. Compute grid cell from canvas position.
     3. Test only nodes in that cell (and possibly immediate neighbors for edge cases).
     4. If the cursor is on a node, test its pins linearly (few pins per node).

**** Rebuild

     The grid is rebuilt whenever the layout changes (topology change, resize, or simulation step).
     Rebuild cost is O(n) -- iterate all nodes, insert into cells. This is cheap even for thousands
     of nodes.

*** EditorState

    Uses orc's existing property system (~NodeProperty<T>~, ~OutputProperty<T>~) instead of
    HashMaps. Properties are attached to the workflow's graph and automatically resize when nodes
    are added/removed or garbage collection runs.

    Positions and sizes are transient -- not persisted to disk. They are computed by the layout
    simulation on app startup and updated in-place during the session. Persistence of UI state is
    a future concern.

    #+begin_src rust
    struct EditorState {
        workflow: Workflow,
        // Properties (attached to workflow graph, auto-resize with topology)
        node_positions: NodeProperty<[f32; 2]>,
        node_sizes: NodeProperty<[f32; 2]>,              // for resizable inspect nodes
        computed_outputs: OutputProperty<Option<OrcHandle>>,   // cached execution results
        nested_exec_state: NodeProperty<Option<NestedExecState>>,  // per-call internal state
        // Spatial index (rebuilt on layout change)
        spatial_grid: SpatialHashGrid,
        // Layout simulation
        layout_converged: bool,                        // false while simulation is settling
        // UI transients (not persisted)
        pan_offset: Vec2,
        zoom: f32,
        selected_nodes: HashSet<usize>,               // NH indices
        connecting: Option<ConnectState>,              // active wire drag from a pin
    }
    #+end_src

*** Incremental Execution

    Computed outputs are stored as ~OutputProperty<Option<OrcHandle>>~. When topology changes
    (connect, disconnect, add/remove node):
    1. Mark affected outputs as stale (set to None).
    2. Propagate staleness downstream through links -- any node whose input comes from a stale
       output also has its outputs marked stale.
    3. On next execution, only evaluate nodes with stale outputs.

    The execution engine needs a modified version of ~Workflow::run~ that:
    - Accepts pre-computed output values for non-stale nodes and skips evaluating them.
    - Returns ALL intermediate output values (not just the final workflow outputs).
    - At NestedCall nodes, recursively captures internal state into ~NestedExecState~.

    Background thread communication: serialize the stale subgraph + its input values via mpsc
    channel, deserialize + run on the background thread, send results back (both the output values
    and any NestedExecState trees). The UI thread stores results into ~computed_outputs~ and
    ~nested_exec_state~. The UI thread never freezes.

    The serialization-to-background-thread approach is necessary because ~Workflow~ is not ~Send~
    (it contains ~Rc<RefCell<...>>~ in the property system). The serialization cost is negligible
    relative to actual execution time.

*** Nested Workflow Execution State

    Each NestedCall node in the outer workflow may be called with different inputs, so each call
    produces different internal values. The state is stored per-call-node and is recursive for
    arbitrary nesting depth.

    #+begin_src rust
    struct NestedExecState {
        // Computed output values for every output pin in this nested workflow's graph.
        // Indexed by OH.index() within the nested workflow's handle space.
        // Vec length matches the nested workflow's graph.outputs.len().
        output_values: Vec<Option<OrcHandle>>,

        // For each node in this nested workflow that is itself a NestedCall,
        // stores that call's internal execution state. Indexed by NH.index()
        // within the nested workflow's handle space. Only NestedCall nodes
        // have Some(...); all other entries are None.
        // Vec length matches the nested workflow's graph.nodes.len().
        child_call_states: Vec<Option<NestedExecState>>,
    }
    #+end_src

    Stored in the outer EditorState as ~NodeProperty<Option<NestedExecState>>~.
    Only NestedCall nodes have Some(...).

    Example with 3 levels of nesting:
    #+begin_src
    Outer workflow: node B (calls "inner"), node C (calls "inner")
    inner workflow: node Y (calls "deep")
    deep workflow:  nodes P, Q (functions)

    Outer EditorState:
      nested_exec_state[B] = Some(NestedExecState {
        output_values: [X_val, Y_val, Z_val, ...],      // inner's OH space
        child_call_states: [.., Some(NestedExecState {   // Y's call to deep
          output_values: [P_val, Q_val],                 // deep's OH space
          child_call_states: [],                         // no further nesting
        }), ..],
      })
      nested_exec_state[C] = Some(NestedExecState {
        output_values: [X_val', Y_val', Z_val', ...],   // different values from B
        child_call_states: [.., Some(NestedExecState {
          output_values: [P_val', Q_val'],               // different from B's deep
          child_call_states: [],
        }), ..],
      })
    #+end_src

**** Populating during execution

     The execution engine captures intermediate output values at every nesting level (current
     ~Workflow::run()~ discards them). After running a NestedCall node, the engine builds a
     ~NestedExecState~ from the intermediate results and stores it. This is recursive -- at each
     nesting level, the engine captures outputs and child states.

**** Loading into nested editor window

     When the user double-clicks call node B:
     1. Clone the nested workflow from ~parent.nested_workflows["inner"]~.
     2. Load B's ~NestedExecState.output_values~ into the new editor's ~computed_outputs~ property
        so the user immediately sees the live computed values for all internal nodes.
     3. Load B's ~NestedExecState.child_call_states~ into the new editor's per-node
        ~nested_exec_state~ property, so that further double-clicks on NestedCall nodes inside the
        nested editor work correctly at deeper levels.
     4. The workflow input chips in the nested editor display B's actual upstream values (the
        arguments that flowed into this specific call).

     When the user then double-clicks Y inside that nested editor window:
     1. Clone the nested workflow from ~inner.nested_workflows["deep"]~.
     2. Load Y's child state from the already-loaded ~nested_exec_state~ property.
     3. Same pattern. Works for arbitrary depth.

*** Nested Workflow Window Lifecycle

    Uses ~ctx.show_viewport_deferred()~ to open real OS-level windows. Each nested editor has its
    own ~EditorState~ and renders identically to the main canvas (same node rendering, same
    interaction, same layout algorithm, same context menu).

    Constraint: opening a nested workflow that is already open in another window is disallowed. The
    app tracks open nested workflows by name and rejects double-click if the workflow is already
    open.

**** Close prompt (nested window, unsaved changes)

     When the user closes a nested workflow window that has unsaved modifications, prompt with 3
     options:
     - *Discard* -- close without saving. All changes are lost.
     - *Replace All* -- overwrite the nested workflow definition in the parent so ALL NestedCall
       nodes that reference this workflow use the updated version.
     - *Create New* -- insert a new nested workflow with an auto-generated name. Update only the
       source NestedCall node (the one that was double-clicked to open this window) to reference the
       new name. All other callers continue to use the original version.

**** Close prompt (main window)

     When the user closes the main window with unsaved changes: Discard / Save (to file).

*** Workflow Inputs/Outputs Display

      layer). They have only an output pin and a label showing the input name. They are roots -- no

    - Workflow outputs are rendered as chip nodes at the last layer (rightmost). They have only an

    - NestedCall nodes are displayed as regular function nodes with the nested workflow name as the

*** Right-Click Context Menu

    The menu opens on a plain right-click, without shift -- shift + right-drag is the pan
    gesture, so the two share the button and are told apart by the modifier.

    Two trigger points with slightly different behavior:

**** Right-click on empty canvas

     Adds a disconnected node at the click position.

**** Right-click on an output pin

     Adds a node AND connects its first input to the clicked output pin. The node is placed at the
     position determined by the layout recomputation after the connection is made.

**** Menu UI (same for both triggers)

     1. A popup appears. The top element is a *text field that is immediately focused* so the user
        can start typing without clicking.
     2. Below the text field is a list of options.
     3. *If the user types into the text field:* the option list is replaced by search results
        filtered from all available functions in the loaded PluginSet. The initial filtering
        implementation is ~name.starts_with(query)~. The filtering logic is behind a trait so it
        can be replaced with levenshtein distance, fuzzy matching, or other strategies later:
        #+begin_src rust
        trait FunctionFilter {
            fn filter(&self, query: &str, functions: &[FuncInfo]) -> Vec<usize>; // indices into functions
        }
        #+end_src
     4. *If the user does NOT type and instead uses arrow keys:* they navigate the default options:
        - "Add Constant Node"
        - "Add Inspect Node"
        - "Session Info..." (opens a separate window showing loaded plugins, their functions, and
          their types -- the information that would otherwise go in a sidebar palette)
     5. Selecting a function from the search results or an option from the default list creates the
        appropriate node. If the menu was triggered from an output pin, the new node's first input
        is also connected to that pin.
     6. After node creation, the layout recomputes.

*** Inspect Node Display

    Inspect nodes are dead-end visualization nodes with 1 input, 0 outputs, and a label string.
    The label determines the display mode.

    - *Text display:* Render the ~deck_to_str()~ output of the connected upstream data in a
      scrollable monospace text area embedded in the node body.
    - *Resizable:* Inspect nodes can be resized by the user (stored in ~node_sizes~ property).
    - *Maximize/minimize:* A toggle to expand the inspect node to fill the viewport, or shrink it
      back to its normal size.
    - *Pop-out:* A button to pop the inspect view into a separate OS window via
      ~ctx.show_viewport_deferred()~. The user can keep this window open as they navigate the
      canvas.
    - *Future 2D/3D viewports:* When the label indicates geometry data, the inspect node will
      embed a wgpu render pass via egui's ~PaintCallback~ and support pan/zoom/orbit within that
      embedded viewport. (Out of scope for initial implementation.)

*** Repaint Strategy

    Reactive mode -- zero CPU when fully idle. ~ctx.request_repaint()~ is called only when needed:

    - Canvas interaction: pan, zoom, box select
    - Pin connection wire drag (drawing the in-progress Bezier to the cursor)
    - Inspect node interaction: scrolling text content, resizing the inspect viewport, future
      pan/zoom/orbit within an embedded 2D/3D viewport
    - Layout settling: while ~layout_converged == false~, request repaint each frame to animate
      nodes settling into place after a topology change or resize. Stops when forces drop below
      the convergence threshold.
    - Execution polling: ~ctx.request_repaint_after(Duration::from_millis(100))~ while a background
      execution is in-flight, to poll the mpsc channel for results. Stops when the result arrives.

    When no interaction is active, no layout is settling, and no execution is running, the app
    sleeps completely and consumes zero CPU.
