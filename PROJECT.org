* TODO Thread Safety in C SDK
  :PROPERTIES:
  :CREATED:  2026-06-07 Sun 15:12
  :END:

  Whenever the plugin code receives an output handle from the host, it has to
  verify that the output handle was allocated in the same plugin. Otherwise it
  is unsafe to write into that memory address. If it came from another plugin,
  then this plugin cannot know anything about the datatype or memory layout. To
  check for this, each plugin likely needs to keep a global list of allocated
  decks, and ensure the output handle matches one of them. Access to this global
  list should be thread safe, since the host can call the plugin functions from
  any thread.

  While this is trivial to do in C++ and Rust, it is not trivial to do in a
  cross platform manner in C. For now, I just have a dummy check that always
  returns true (safe). This is good enough for a prototype, but at some point we
  need to figure out a good cross platform thread API for our C SDK.

  Should the host provide the thread API too? How does Parasolid handle it?

  good litmus test to judge the quality of this new system, once enough details
  are fleshed out. =Objectify= implements structs on top of Grasshopper. The
  user can compose arbitrary data into their own struct, pass it around their
  file, and later access members of that struct. It is a minor convenience, and
  was trivial to implement in GH. Trying to do the same in Kratos turned into a
  dumpster fire. That is what makes this a good litmus test.

  <2026-08-01 Sat 18:42> It seems fairly trivial to do this with built-in types, and with types that
  are internal to the plugin that is trying to implement this. Just make a generic dictionary type
  that stores all data in a tagged union, or a heap allocated OOP thing or whatever. And make a
  block that takes variadic inputs of different types, and names, and outputs a this dictionary. The
  first input could be a list of names, and the remaining inputs could each represent one member of
  the object / dictionary. Probably fine to do the usual list processing on such inputs, but
  requires a bit of thought.

  It seems very unwieldy to try and get this to work with types that are opaque to another
  plugin. That would require some sort of shared strategy between the plugins, and possible between
  the host and the plugins, for type erased storage of objects in a container. That can be done in
  theory with something that resembles a v-table, but not worth it. Very ugly, and likely not useful
  at all. This is possible trivially in C# (Grasshopper), because it is C#.

** TODO Host program that runs as a service
   :PROPERTIES:
   :CREATED:  2026-08-26 Wed 10:52
   :END:

   Server / service that listens for requests, and performs work by calling plugin functions when it
   receives a request. This is interesting, as I can probably run a workflow on multiple threads
   using make, of course, assuming the host program can schedule the jobs it receives on all
   available threads.

   A client would:
   - Start a session, and receive a session id from the service. This helps the service distinguish
     the requests it receives from different clients in the future.
   - Create constants containing primitive datatypes, by passing them in as either binary blobs or
     strings. The server returns an id representing the constant that lives in the server's memory,
     associated with that particular sesion.
   - Call functions with specific inputs. The client specifies inputs by their ids. The server runs
     the funciton, and returns ids corresponding to the inputs.
   - Presumably some of these functions export files, that are received by the client as the output
     of their workflow.
   - Client can request to download the workflow they built up during this session as a serialized
     workflow.
   - The client can then close the session, which will cause all the session data, variables,
     registry etc. to be cleaned up.

   Comparing this to the host programs I have now, each session will have it's own OrcHost instance,
   registry, allocators, etc.

  A node-editor UI app that wants to create nodes with properly named inputs needs to get that
  information from the plugin that defines the corresponding function. This will require adding new
  fields to the function metadata's ABI. It certainly needs to be flexible, and allow for the host
  app to overwrite the behavior if need be.

  Requires more thought as to what the new metadata will be. I need to come up with a proper
  algebraic datatype that supports all the below cases. These apply for both inputs and outputs. I
  am using 'arguments' as a general term for both inputs and outputs:

  1. Fixed number of arguments with all their types known.
  2. Fixed number of arguments, with some of the types known.
  3. Fixed number of arguments, where none of the types are known.
  4. Variadic arguments, all of a single known type.
  5. Variadic arguments, where none of the types are known.

  Once this is implemented, and used, based on that experience it might be good to add more things
  to this metadata to improve the overall experience. But no matter what, it should remain purely
  metadata. The actual function should still handle everything procedurally. Should be completely
  optional. Everything should still work without this metadata, albeit a more inconvenient manner.
